## Goal

Make it easy to inspect machine-local PM project bindings and add a registered project as a child without manually copying its project ID, repository path, Git remote, alias, and relative path.

## Proposed implementation

- Add a CLI command that lists the verified projects in the local project registry without requiring them to already be declared in the active project's linked-project manifest.
- Add a guided command for selecting a registered project and creating a child declaration in the active project.
- Read the stable project ID and verified checkout path from the registry.
- Inspect the checkout's credential-free Git origin and use it as the proposed portable `repositoryUrl`.
- Suggest a normalized alias from project metadata or the repository directory name.
- When the checkout is inside or adjacent to the active repository, suggest a normalized relative `pathHint`.
- Show the complete declaration and require confirmation before writing it in interactive mode.
- Preserve explicit flags for scripting and non-interactive use.
- Never modify the registered child repository; configuring its reciprocal parent declaration remains a separate action.

## Acceptance criteria

- Users can list registered project IDs and verified checkout paths through the CLI without reading registry JSON files.
- A registered project can be added as a child using a concise selector-based command.
- Inferred repository URLs exclude embedded credentials and fail clearly when no portable origin is available.
- Alias and path-hint suggestions are deterministic, validated, and overridable.
- Existing duplicate ID, duplicate alias, self-link, and manifest validation rules remain authoritative.
- The command works when no relative path hint can be inferred, relying on the machine-local registry binding.
- Tests cover listing, inference, confirmation, non-interactive use, invalid remotes, and duplicate declarations.
- The linked-project guide documents both the explicit and convenience workflows.
