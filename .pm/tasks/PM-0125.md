## Goal

Advance PM's release version monotonically from its own completed tasks and delivered milestones without coupling version changes to arbitrary commits.

## Implement

- For an opted-in versioned project, increment patch exactly once when a task transitions from a non-done state to done.
- Increment minor and reset patch to zero when a milestone delivery record is accepted.
- Never decrement a version when a task or milestone is reopened; define redelivery as a new minor release and re-completion as a new patch event.
- Keep major advancement behind an explicit authoritative operation with a previewable reason; never infer it from ordinary work.
- Make task state, milestone delivery, and version advancement one recoverable mutation boundary so partial writes cannot disagree.
- Make retries and reconciliation idempotent so an already recorded completion or delivery cannot bump twice.
- Exclude release-promotion commits, OCI digest pinning, documentation-only commits outside PM task completion, and other Git history from automatic advancement.
- Emit structured version-transition evidence that release automation can distinguish as task, milestone, or manual-major.
- Exercise the bootstrap cutover defined by PM-0124 without double-counting PM-0124 or this task.

## Acceptance criteria

- Completing one task advances `1.4.6` to `1.4.7` exactly once.
- Delivering one milestone advances `1.4.7` to `1.5.0` exactly once.
- Reopen, retry, validation failure, and interrupted-write scenarios never decrement or duplicate a version.
- Projects without configured release versioning do not acquire version mutations.
- A manual major transition is explicit, auditable, and cannot occur through normal task or milestone operations.
- Release tooling receives enough persisted evidence to choose the correct immutable and moving Action refs.
- Service, CLI, MCP, and repository-recovery tests cover the complete transition contract.
