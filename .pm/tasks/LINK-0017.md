## Goal

Let someone browsing a linked child project open that child's Settings page and manage its milestones and activation gates without losing project context.

## Problem

The task sidebar always links to `/tasks/settings`, linked-project routing has no Settings child route, and Settings API clients use active-project URLs. From `/projects/{projectId}/tasks`, opening Settings therefore returns to the primary project. Milestone and activation views and edits for the child are unavailable, and a superficial routing change would risk showing child context while operating on parent data.

## Proposed implementation

- Add a project-qualified Settings route, using `/projects/:projectId/tasks/settings` within the linked task shell.
- Derive the Settings link and active state from `ProjectContextService` so navigation preserves the selected project.
- Make Settings and Activation API clients use the selected project's API prefix for every project-owned read, preview, and mutation.
- Clearly identify the selected project in the page heading and preserve project switching, task/wiki mode navigation, and dirty-route protection.
- Treat General, Statuses, Tracks, Milestones, and Activation as project-owned sections.
- For readable but untrusted children, show the project-owned data in a deliberate read-only state with mutation controls disabled and a concise write-trust explanation.
- Do not show or operate parent data inside child context. Host/control-plane sections such as local link registry/trust and agent runners must remain explicitly host-scoped, be separated from child project settings, or be unavailable while a child is selected.
- Preserve current-project `/tasks/settings` behavior.
- Cover narrow/mobile routing and keyboard/focus behavior using the existing Settings interaction grammar.

## Acceptance criteria

- Opening Settings from a selected child keeps the child selected and uses a canonical project-qualified URL.
- The page displays the child's name, statuses, tracks, milestones, activation triggers, requirements, provenance, and lifecycle state.
- On a write-trusted child, milestone and activation CRUD/lifecycle actions affect only that child and refresh the child view.
- On an untrusted readable child, the same project-owned sections remain inspectable but cannot be mutated.
- Switching among Tasks, Wiki, and Settings preserves the selected project.
- No section in child Settings silently reads or mutates the primary project's data.
- Current-project Settings and static/read-only behavior continue to work.
- Route, API-client, trust-state, accessibility, and responsive tests cover the selected-project workflow.
