## Goal

Evaluate whether PM should be rebranded as **Tracks** before the project develops a stable public package identity. This is a discovery and decision task only; creating it does not authorize or commit the repository to a rename.

## Questions to answer

- Does Tracks communicate the product better than PM across task management, milestones, wiki, MCP, static publishing, and agent-run supervision?
- Is the name sufficiently distinctive and searchable, or too generic and collision-prone?
- Are suitable GitHub, NuGet, executable, domain, and package-manager identifiers available?
- Should the product name, executable command, repository name, package ID, and on-disk project directory all change together or remain partially compatible?
- Would `tracks`, `trk`, or the existing `pm` be the preferred terminal command?
- Does the existing concept of task tracks make the product name clear, or make phrases such as “Tracks tracks” awkward?
- What migration burden would existing users and repositories accept?

## Inventory

Identify every public and persisted naming surface, including:

- repository and GitHub Pages URLs
- assembly, namespace, solution, project, and package names
- NuGet tool ID and executable command
- MCP server name and client configuration
- `.pm/` project directory and project discovery
- OS identity/config directories and environment variables
- Worker names, endpoints, headers, signing protocol identifiers, D1 data, and Cloudflare configuration
- Angular titles, routes, static exports, documentation, examples, screenshots, and release artifacts
- task IDs and the internal `PM` track, which do not necessarily need historical rewriting

## Options to compare

1. Keep **PM** everywhere.
2. Use **Tracks** as the product name while retaining `pm`, `.pm/`, protocol identifiers, and compatibility-sensitive internals.
3. Rebrand public surfaces and introduce new command/config names with compatibility aliases.
4. Perform a complete rename with an explicit migration period.

Evaluate user clarity, distinctiveness, migration cost, backward compatibility, package availability, discoverability, and maintenance complexity for each option.

## Deliverable

Write a short decision record in the PM wiki containing:

- the recommended name and rationale
- naming and package availability research
- the selected command, package ID, repository name, and public terminology
- compatibility policy for `pm`, `.pm/`, existing environment variables, MCP configuration, and signed Worker requests
- migration and deprecation stages if a rename is selected
- an explicit list of identifiers that remain unchanged
- follow-up implementation tasks split into safe, reviewable slices

Do not rename files, namespaces, commands, storage directories, Worker identifiers, or public endpoints in this task.

## Relationship to releases

- Keep this task non-blocking and without a dependency from PM-0070.
- Before the first stable public NuGet publication, explicitly review this decision so an irreversible package identity is not chosen accidentally.
- If no rebrand decision has been accepted, PM-0070 continues using the planned `Chronium.PM` package and `pm` command.

## Validation

- Search the complete repository for public and persisted PM identifiers.
- Check relevant public naming/package availability at the time the decision is made.
- Verify that the decision record accounts for existing projects, identities, MCP configurations, Worker authentication, and release artifacts.

## Acceptance criteria

- The project has an explicit keep-or-rebrand decision rather than an informal preference.
- The full compatibility and migration cost is understood before implementation.
- No existing repository, identity, Worker, or installation is changed by this discovery task.

## Notes

- 2026-07-27 08:45 UTC - Preliminary naming research found a significant direct collision with TracksApp/tracks, an active self-hosted GTD/task-management web application using the bare “Tracks” name (1.2k+ GitHub stars, active commits in 2026, getontracks.org). Bare Tracks is also generic, difficult to search, and likely a weak software mark. The npm and PyPI names “tracks” are occupied; tracks.dev is occupied by an unrelated Track Contents Manager; trackspm.com has been registered since 2021, although it currently serves no meaningful public page.
  
  Promising identifiers were available when checked: GitHub chronium/tracks; NuGet Tracks, TracksPM, Tracks.PM, and Chronium.Tracks; scoped npm @chronium/tracks; and no Homebrew formula named tracks. tracks.pm returned an AFNIC NOT FOUND response, while gettracks.dev and trackspm.dev had no DNS response, but domain availability must be rechecked through a registrar before relying on it.
  
  Recommendation from this pass: do not use bare Tracks as the formal product identity. If the idea proceeds, compare “Tracks PM” with the more distinctive “Chronium Tracks”; retain pm and .pm as compatibility-sensitive technical identifiers initially. A possible presentation is “Tracks PM” with the descriptor “Local-first project management for humans and agents.” This is preliminary product research, not trademark clearance.
- 2026-07-27 09:01 UTC - Follow-up branding research broadened the task beyond Tracks.
  
  Tracks should be dropped from the shortlist. Beyond the direct TracksApp collision, the word naturally implies time tracking, work tracking, telemetry, or analytics, and the product already uses “track” as an internal grouping noun.
  
  Several semantically attractive alternatives also have meaningful collisions:
  - Project Memory is a current developer project-state product, with other project-memory/MCP tools nearby.
  - Planfile is a current SDLC/project-management CLI with MCP and agent automation.
  - Threadmark is used by current software products.
  - Charter is both a standard project-management artifact and a current AI-governance tool for coding-agent projects.
  - Planfold, Planroot, Planstead, Planary, SourcePlan, and RepoBrief are occupied.
  - Projectfile is extremely generic in developer ecosystems.
  - CommitPlan has several exact-name GitHub repositories.
  - RepoState has comparatively little direct brand competition, but reads like a low-level Git/repository status utility rather than a complete project-management product.
  
  The category itself is becoming crowded. Harness uses “project management for humans and agents” verbatim. Sfora already positions a repository-local Markdown workspace with tasks, docs, and MCP. Decapod, BlocPad, epiq, and others also emphasize durable repo-native project state. The product should therefore lead with its specific philosophy rather than generic “agent-friendly” language.
  
  Current recommendation:
  1. Keep the public name PM for now, presented as Chronium PM where distinctiveness is needed.
  2. Keep the command, package direction, repository, and .pm directory unchanged.
  3. Consider “Project Model” as an explanatory expansion of PM, not necessarily a formal rename. It reflects the shared model exposed through CLI, web, MCP, and static publishing better than “tracker.”
  4. Lead with a concise position such as “Project state, committed.” Supporting copy can say “Tasks, knowledge, and agent context live with the repository.”
  5. Retain RepoState and CommitPlan only as secondary naming candidates; neither is clearly stronger than Chronium PM.
  
  This remains preliminary market screening, not trademark clearance.
- 2026-07-27 09:05 UTC - The current leading naming direction is **Project Model**, retaining **PM** as the visible short name. This fits the product architecture: tasks, milestones, wiki knowledge, dependencies, priorities, members, and future agent runs form one repository-owned model exposed consistently through CLI, web, MCP, and static publishing. It avoids tracker/timekeeping connotations and requires no compatibility rename. Before finalizing, evaluate whether the generic software-modeling meaning creates material confusion and settle the exact public lockup, descriptor, and capitalization.
