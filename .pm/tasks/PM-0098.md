Follow the Milestone Deliverables and Activation Triggers architecture wiki entry.

## Goal

Complete activation trigger definition management in the Angular Activation settings surface after trigger creation is available.

## Scope

- Rename a trigger title without changing its immutable key.
- Edit requirements for inactive triggers through the ordinary definition workflow.
- Route requirement changes for active triggers through the existing redefine preview and confirmation workflow so latching semantics are never bypassed.
- Remove a trigger only when the application service permits it, presenting active state, consuming milestones, and other blockers through contextual, confirmable actions.
- Reuse the shared search-backed requirement editor introduced by PM-0097.
- Refresh switchboard state and milestone trigger choices after every successful mutation.
- Use existing revision preconditions, problem details, project refresh, and external-change handling.

## Acceptance criteria

- Owners can rename, edit, redefine, and remove trigger definitions from the Activation settings UI.
- Inactive requirement changes use the ordinary endpoint; active changes always use redefine preview and confirmation.
- Destructive removal is contextual and confirmable, and application-service blockers remain visible and actionable.
- Mutation success refreshes the switchboard and milestone trigger choices without losing the current Settings context.
- Stale revisions, validation failures, unavailable sources, and removal guards produce localized actionable errors without losing drafts.
- Read-only and static projects expose no definition controls.
- Keyboard order, visible focus, accessible names, dialog dismissal, mobile layout, and reduced-motion behavior follow existing UI patterns.
- Component, store, Storybook, and focused browser tests cover rename, inactive editing, active redefine, guarded removal, revision conflicts, and read-only behavior.
