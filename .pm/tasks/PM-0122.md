## Goal

Make Project Model consume its own published Action through a static-site workflow that is independent from the workflow that builds and promotes the Action/runtime.

## Implement

- Keep the Action and OCI build, validation, publication, and ref promotion in the release workflow.
- Add a separate PM site-publishing workflow that checks out the repository and invokes `chronium/pm@latest`.
- Run `command: doctor` before generating the site.
- Run `command: site-build` for PM's configured published Overview and static task/wiki experience.
- Upload and deploy the generated output through the repository-owned GitHub Pages steps.
- Ensure the publishing workflow does not invoke a local PM build, directly pull the OCI image, or call an unpublished checkout-local Action.
- Trigger site publication only from an already promoted Action release, with an explicit manual rerun path.
- Record the resolved PM version, Action revision, and OCI digest in the workflow output.
- Provide an immutable Action-ref override for rollback and incident recovery.

## Acceptance criteria

- Two workflows own distinct responsibilities: one publishes PM Action/runtime releases; the other consumes the public Action to publish PM's site.
- PM's site workflow uses `chronium/pm@latest` for both validation and export.
- A broken or unpromoted Action cannot be mistaken for a successful PM dogfood deployment.
- Invalid PM project state stops publication before Pages artifact upload.
- The deployed site retains PM's Overview-first behavior, tasks, wiki, search, accent, and static navigation.
- The site workflow can be manually rerun against a known-good immutable Action ref.
