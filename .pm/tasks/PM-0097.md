Follow the Milestone Deliverables and Activation Triggers architecture wiki entry.

## Goal

Let project owners manage activation trigger definitions from the Angular Activation settings surface without falling back to the CLI.

## Scope

- Create a trigger with an immutable key, editable title, and zero or more task or milestone requirements.
- Treat an empty requirement list as an intentional manual-only trigger and explain that consequence before saving.
- Rename a trigger title without changing its key.
- Edit requirements for inactive triggers through the ordinary definition workflow.
- Route requirement changes for active triggers through the existing redefine preview and confirmation workflow so latching semantics are never bypassed.
- Remove a trigger only when the application service permits it, clearly presenting active state, consuming milestones, and other blockers instead of hiding the action.
- Keep milestone attachment and detachment in the existing deliverable editor while ensuring newly created, changed, and removed definitions refresh there immediately.
- Use the existing revision preconditions, problem details, project refresh, and external-change handling rather than introducing a parallel mutation path.

## Acceptance criteria

- Owners can create, rename, edit, and remove trigger definitions from the Activation settings UI.
- Requirement editing supports both task and milestone sources, rejects duplicates, validates referenced sources, and provides a practical selection/search workflow for realistic projects.
- Manual-only creation is explicit; active requirement changes use redefine; destructive removal is contextual and confirmable.
- Mutation success refreshes switchboard state and milestone trigger choices without losing the current settings context.
- Stale revisions, validation failures, unavailable sources, and removal guards produce localized actionable errors.
- Read-only and static projects expose no definition controls.
- Keyboard order, visible focus, accessible names, dialog dismissal, mobile layout, and reduced-motion behavior follow existing UI patterns.
- Component, store, Storybook, and focused browser tests cover creation, editing, guarded removal, revision conflicts, and read-only behavior.
