## Goal

Allow one PM project to authorize independent user identities on multiple machines while keeping `.pm/` public and every private signing key in that machine's OS user configuration.

The immediate workflow is:

1. An existing project admin creates a short-lived invitation on the Mac.
2. The repository, including its public `.pm/project_id.txt`, is cloned on Linux.
3. PM generates or loads the Linux user's independent local identity.
4. The Linux user accepts the invitation and becomes a project member.
5. Signed next-ID operations work from either machine without copying private keys.

## Membership model

- Preserve the existing Worker `project_members` model and `admin` / `user` roles.
- Project creators remain the initial admin.
- Both roles may perform ordinary authenticated project operations such as allocating and peeking task IDs.
- Only admins may create invitations, list/manage membership, change roles, or remove members.
- Prevent removal or demotion of the final admin.
- Do not store membership lists, invite secrets, public keys, or roles in `.pm/`; the public project ID remains the only repository-side identity reference.
- Recovery-key activation, key rotation, organizations, and Worker-administrator access remain separate future work.

## Invitation design

- Add a D1 migration for project invitations with project, cryptographically random token hash, intended role, creator, creation/expiry timestamps, and consumed/revoked state.
- Invitation tokens are high-entropy secrets, shown once, stored only as hashes, single-use, explicitly expiring, and never written to logs.
- Let an admin choose `user` or `admin` when creating an invitation; default to `user` and use a conservative default expiry.
- Invitation acceptance must be signed by the joining identity and bind the supplied user ID, display name, and P-256 public key to the membership row.
- Reject expired, revoked, consumed, malformed, cross-project, replayed, or incorrectly signed invitations without revealing project membership details.
- Consume an invitation atomically with member insertion so retries cannot create inconsistent state.

## Worker API

- Add authenticated endpoints to list project members, create/revoke invitations, update a member role, and remove a member.
- Add a signed invitation-acceptance endpoint that authenticates the joining identity's proof of private-key possession before it is a member.
- Centralize admin authorization and final-admin protection in Worker helpers.
- Return stable structured errors while preserving the rule that Worker logs never include signatures, invite tokens, recovery keys, credentials, or request paths.
- Extend the fake D1 test harness and deploy a reviewed remote migration only after local tests pass.

## PM application and CLI

- Extend `INextIdService` behind an application-level project membership service rather than issuing HTTP requests directly from commands or UI code.
- Add a project membership CLI surface for list, invite, join, role change, invitation revocation, and member removal.
- Make invitation acceptance prompt securely or accept stdin so the token does not have to enter shell history.
- Add an identity inspection command that shows only the shareable user ID, display name, and public key/fingerprint.
- Clearly distinguish local identity, public project ID, membership role, and recovery key in command output and documentation.

Example flow:

```sh
# Existing admin on the Mac
pm project invite --role admin --expires 24h

# New identity on the Linux clone; token is entered through a hidden prompt
pm project join

pm project members
```

Exact command naming may follow the established Spectre CLI conventions, but joining must not require copying the original machine's identity file.

## MCP parity

- Add normal-mode tools to list members, create/revoke an invitation, accept an invitation, update roles, and remove a member.
- Mark membership mutations accurately as destructive or sensitive in MCP annotations.
- Return invitation secrets only from explicit invitation creation and never from list/read tools.
- Exclude every membership administration tool from the `run-worker` restricted MCP profile.

## Web parity

- Add a Project members section to Angular settings showing display name, user ID/fingerprint, role, and current local identity.
- Provide focused dialogs for creating an invitation, changing a role, revoking an invitation, removing a member, and joining with a pasted invitation.
- Display an invitation secret once with copy and acknowledgement behavior; do not retain it in browser storage or later API responses.
- Handle unauthorized, final-admin, expired-invite, stale revision, offline Worker, empty, loading, and permission-restricted states.
- Keep administrative controls unavailable to normal users while still allowing them to see their own membership and project authentication health.

## Security requirements

- Never transfer or clone a private identity key between machines.
- Never commit invitation tokens, membership credentials, or identity files.
- Sign all member and invitation operations with the existing canonical-request mechanism and nonce protection.
- Use constant-time hash comparison where applicable and atomic D1 statements for consume/remove/role invariants.
- Rate-limit or otherwise bound invitation acceptance attempts within the Worker's personal-utility threat model.
- Treat an admin invitation as equivalent to granting project administration and make that explicit in CLI and web confirmation text.

## Tests

- Worker: admin/user authorization, invitation creation, secure hashing, expiry, revoke, single use, atomic acceptance, replay, wrong project, bad signature, role updates, member removal, final-admin protection, and redacted failures.
- .NET: membership service request signing and errors, CLI flows, secure token input, missing project/identity, and unchanged next-ID behavior.
- MCP: schemas, annotations, allowed/denied roles, secret omission, and exclusion from the run-worker profile.
- Angular/API: member listing, invitation lifecycle, join flow, role/removal confirmation, permission states, escaping, stale revisions, and secret non-retention.
- Cross-machine smoke: create an admin invitation on macOS, accept it from a fresh Linux identity, allocate IDs from both identities, revoke the Linux member, and verify subsequent signed allocation is denied.

## Validation

- Run Worker tests and local D1 migration.
- Run the .NET build and tests.
- Format Angular changes and run the relevant frontend validation gates.
- Run project validation.
- Review and apply the remote D1 migration, deploy the Worker, and repeat the two-identity smoke against the deployed endpoint.

## Acceptance criteria

- A cloned project works from Linux after invitation acceptance without copying the Mac identity.
- Admin and user roles are enforced consistently across Worker, CLI, MCP, API, and web.
- Removing a member immediately prevents future authenticated ID allocation by that identity.
- The final admin cannot be removed or demoted.
- `.pm/` remains a public artifact containing no new secret.
- Existing single-user projects continue working without migration steps beyond the deployed D1 schema migration.

## Implementation outcome

- Invitations are fixed at 24 hours, role-bound to `admin` or `user`, hashed at rest, single-use, revocable, and acceptance-rate-limited.
- Membership is Worker-owned and exposed consistently through the CLI, normal MCP profile, local JSON API, and the focused Angular settings component.
- D1 migration `0004_project_invitations.sql` and Worker version `1c08893c-f54a-4b64-840c-9e1e637c571e` were deployed on 2026-07-27.
- The production smoke used a disposable Linux/XDG identity, verified allocation from both identities, removed the Linux member, verified subsequent allocation denial, and removed all temporary local files and tasks.
