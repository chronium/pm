## Goal

Allow trusted MCP clients to inspect milestone deliverables and activation state in any readable project in the linked family without changing the active repository.

## Scope

- Add an optional `project` selector to `get_project`, `list_milestones`, and `get_activation_switchboard`.
- Accept the established selector forms: `current`, `parent`, stable project ID, or unique alias.
- Resolve the selected readable project through the existing linked-family rules, then construct activation resolution and validation from that project's `ProjectRoot`.
- Include structured owning-project metadata and linked-resolution warnings in returned payloads while keeping omitted-selector current-project usage compatible.
- Keep activation state project-local: task and milestone requirements must resolve only within the selected project, even when another family member uses the same task or milestone key.
- Preserve the run-worker boundary: it may read the current project's switchboard, but linked-project selectors are rejected with the established project-scope error.
- Remove active-project-only helper paths superseded by the selected-project read path.

## Acceptance criteria

- Normal MCP reads succeed by alias, stable project ID, and `parent`, and report the selected project's identity, revision, relationship, and dirty state.
- Missing, ambiguous, and unavailable project selectors return the same structured errors and warnings used by existing linked reads.
- Duplicate task or milestone IDs in another family member cannot affect the selected project's trigger satisfaction or milestone lifecycle.
- Omitting `project` preserves current-project responses for existing clients.
- Run-worker reads remain current-project-only and no activation mutation capability is added.
- Focused service and stdio MCP integration tests cover current, linked, unavailable, ambiguous, and restricted-profile cases.

## Deferred follow-on

Target-scoped trigger mutations, activation/override/reset/reconciliation, milestone delivery/reopening, and any family-wide aggregate listing will be planned as separate tasks after this read seam is established.
