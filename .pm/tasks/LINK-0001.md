## Goal

Turn DISCOVERY-0001 and the resolved product decisions into the normative linked-project design before persistence contracts are implemented.

Create the source-of-truth design at `.pm/wiki/architecture/linked-project-federation.md`.

## Resolved decisions

- A project has zero or one parent. General project graphs and multiple parents are out of scope.
- Linked projects do not inherit configuration, tracks, milestones, statuses, tasks, wiki content, or authority. Every project remains independently valid and useful.
- The parent declares and orders its direct children. Stable project IDs are authoritative; human-readable aliases and paths are resolution aids.
- Store portable path hints in committed project metadata and keep machine-specific path bindings in user-local configuration.
- The active project is the default command target. CLI and MCP operations may accept an optional explicit project selector.
- Family-wide reads cover tasks and wiki content. Reads use each available project's current working tree.
- Missing parents, children, or siblings produce visible warnings but never prevent the active project from opening or operating independently.
- An unresolved cross-project task dependency is treated as blocked with a warning rather than as satisfied or as a fatal project error.
- Cross-project writes require explicit targeting and project-level local write trust. One operation mutates at most one repository in the first version.
- Coordinated atomic changes across multiple repositories are future work.
- Static exports initially link to separately published project sites. Bundled family exports are future work.
- Remote runs may receive immutable linked task and wiki context, but the runner does not gain authority to mutate sibling repositories.
- Provide an explicit command for creating, inspecting, and repairing local path bindings instead of silently guessing writable locations.

## Proposed implementation

- Define the zero-or-one-parent family model, parent-owned child ordering, local aliases, and stable project-ID references.
- Define committed path hints plus user-local path bindings and their resolution precedence.
- Specify canonical project-qualified task and wiki references.
- Specify degraded resolution states, warnings, cycle and duplicate handling, and standalone behavior.
- Describe active-project and family traversal for CLI, MCP, Angular, search, next-task ranking, static publishing, and agent context.
- Define project-level write trust and the single-repository mutation boundary.
- Include concrete examples for a `games` parent repository with `royale` and a second game as Git submodules.
- Record migration behavior: existing standalone projects require no changes until they opt into linking.

## Acceptance criteria

- The target wiki page contains one source-of-truth design with examples and explicit non-goals.
- The note defines persistence ownership, discovery and resolution precedence, canonical references, read behavior, and write boundaries.
- Missing linked projects never disable the active project.
- Decisions from DISCOVERY-0001 are captured without unresolved inheritance or topology ambiguity.
- The Games, Royale, and second-game scenario is worked through for task lookup, wiki lookup, dependencies, local path repair, static sites, and remote-agent context.
- The note identifies bundled static publishing and coordinated multi-repository mutation as future work.
- No application behavior is implemented in this task.
