## Goal
Allow a PM project to register one or more repository directories as read-only static resource providers for wiki images and other project documentation assets. A project such as ChronoFall should be able to register its `docs` directory and reference committed images from wiki Markdown without embedding them as data URLs or moving them under `.pm`.

## Proposed implementation
- Extend project configuration with named static resource providers, each mapping a stable provider key to a repository-relative directory.
- Add modeled application-service operations to list, add, update, and remove providers while preserving existing project configuration behavior.
- Validate provider keys and paths. Reject absolute paths, traversal outside the repository, missing or non-directory targets where appropriate, duplicate keys, and symlink resolutions that escape the configured root.
- Serve registered files from a stable namespaced route such as `/resources/{provider}/{**path}` with correct MIME types, HEAD support, cache headers, and safe not-found responses.
- Never expose unregistered project files, directory listings, hidden PM identity/configuration data, or paths outside the provider root.
- Define a durable Markdown reference form for provider resources and resolve it consistently in wiki read views and editor previews. Prefer a form that remains understandable in raw Markdown and does not depend on the current wiki page depth.
- Include referenced providers in generated static sites, preserving stable URLs and copying only files under registered roots.
- Make linked-project wiki resources resolve against the owning project rather than the currently active project.
- Expose provider management through the CLI and Angular project settings/API. Keep the underlying configuration suitable for future MCP parity.
- Document setup and usage with an image example based on a registered `docs` provider.

## Acceptance criteria
- A project can register multiple named repository-relative resource directories.
- Wiki Markdown can render an image from a registered provider in hosted PM web, editor preview, and generated static sites.
- Resources from the active project and read-only linked projects resolve from the correct owning project.
- Unregistered files, traversal attempts, encoded traversal, and symlink escapes return safe failures.
- Renaming or removing a provider produces a clear broken-resource state without rewriting wiki Markdown silently.
- CLI, API, Angular settings, renderer, static generator, and security behavior have focused automated coverage.
- Existing external HTTPS images and Markdown sanitization continue to work.
