## Goal

Expose the project-owned Settings and milestone-activation HTTP surface for a selected readable or write-trusted linked project, so a web client launched from a parent can safely inspect and mutate the child without changing the parent repository.

## Problem

The linked-project API currently exposes only a readable `GET /api/v1/projects/{projectId}/settings`. Settings mutations and the entire activation/lifecycle surface remain available only under the active project's `/api/v1/settings` and `/api/v1/activation` routes. Adding linked Settings navigation before fixing this boundary could present child context while silently mutating the parent.

## Proposed implementation

- Add selected-project routes under `/api/v1/projects/{projectId}` for the project-owned Settings operations needed by General, Statuses, Tracks, and Milestones.
- Add selected-project activation routes for switchboard reads, trigger CRUD, requirement preview/redefinition, manual activation and override, reset, reconciliation, milestone required-trigger changes, delivery previews, delivery, and reopening.
- Resolve every route through the existing linked-project target and its `ProjectConfigService`, `ActivationTriggerService`, `MilestoneDeliveryService`, and revision service.
- Permit reads for readable linked projects and require local write trust for every mutation.
- Preserve the current API's ETag, `If-Match`, preview-revision, validation, error, and mutation-impact semantics.
- Reuse shared endpoint/application behavior instead of maintaining a second copy of activation or settings business rules.
- Keep host control-plane operations such as registry binding and local write trust outside this selected-project surface.

## Acceptance criteria

- A parent-hosted PM web server can read a child's settings and activation switchboard through project-qualified endpoints.
- Every supported mutation changes only the selected child's files and returns selected-project data/revisions.
- An untrusted but readable child remains readable and rejects all mutations with a clear trust error.
- Stale configuration and preview revisions are rejected consistently with current-project operations.
- Tests prove the parent repository remains unchanged during child settings, trigger, and milestone lifecycle mutations.
- The generated OpenAPI client includes the selected-project contracts.
- Existing current-project endpoints retain their behavior without compatibility-only duplicate implementations.
