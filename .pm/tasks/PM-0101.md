## Goal

Allow trusted MCP clients to manage milestone deliverables and activation trigger definitions in a selected write-trusted linked project.

## Scope

- Add an optional `project` selector to milestone definition tools: `add_milestone`, `rename_milestone`, `remove_milestone`, `set_milestone_priority`, and `set_milestone_description`.
- Add the same selector to trigger definition tools: `add_activation_trigger`, `rename_activation_trigger`, `remove_activation_trigger`, `set_activation_trigger_requirements`, `attach_activation_trigger_to_milestone`, and `detach_activation_trigger_from_milestone`.
- Resolve mutations through the established linked-project write-trust checks and construct target-scoped config, activation, validation, persistence, and revision services.
- Validate requirements, milestone ownership, activation cycles, and task-placement relationships entirely within the selected project.
- Return mutation receipts containing the owning project ID and paths relative to that repository.
- Reread the authoritative switchboard from the selected target after every successful mutation.
- Keep all definition controls unavailable to the run-worker profile, including current-project mutations.
- Remove active-project-only mutation helpers superseded by the target-scoped path.

## Acceptance criteria

- Every scoped definition tool supports `current`, `parent`, stable project ID, and unique alias.
- Unreadable, unavailable, untrusted, ambiguous, and binding-mismatched targets fail before writing.
- A rejected mutation leaves the selected repository byte-for-byte unchanged.
- Receipts and immediate rereads identify and describe the same target project.
- Identical task, milestone, or trigger keys in another family member do not affect validation.
- Existing omitted-selector current-project behavior remains compatible.
- Focused service and stdio MCP tests cover successful linked mutations, trust denial, cycle rejection, receipt paths, and run-worker denial.

## Out of scope

Trigger activation transitions, reconciliation, redefinition of active triggers, and milestone delivery/reopening are handled by subsequent tasks.
